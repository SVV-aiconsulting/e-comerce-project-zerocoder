# Персональные данные и электронный реестр согласий

## Публичные документы

- действующая Политика: `/privacy-policy/`;
- действующее Согласие: `/personal-data-consent/`;
- постоянные URL действующей версии 1.1: `/privacy-policy/v/1.1/` и
  `/personal-data-consent/v/1.1/`; версия 1.0 сохранена по прежним URL;
- отзыв на сайте: `/personal-data-withdrawal/`;
- отзыв в Telegram/VK: команда `/privacy_withdraw`.

Для ссылок из внутренних bot-контейнеров backend использует `PUBLIC_SITE_URL`,
если переменная задана, иначе публичный origin из `YOOKASSA_RETURN_URL`. Поэтому
бот не отправляет клиенту недоступный Docker-адрес `http://web:8000`.

Версии создаются в `PersonalDataDocumentVersion`. Опубликованную запись нельзя
изменить: для новой редакции следует создать новую версию с новой датой и
постоянным URL. SHA-256 полного текста рассчитывается сервером. Новая действующая
версия автоматически делает прежнее согласие недостаточным и вызывает повторный
запрос у пользователя.

## Сценарии

Сайт не использует IP или cookie как CRM-идентификатор клиента. В каждой новой
Django-сессии AI-диалог сначала показывает ссылки на оба документа и отдельные
кнопки «Согласен»/«Не согласен»; поле сообщения появляется только после согласия.
Ручная форма использует отдельный заранее не отмеченный чекбокс. В пределах той
же сессии действующее согласие повторно не запрашивается.

Telegram, VK и MAX используют устойчивый ID аккаунта конкретной платформы.
Backend проверяет действующее согласие до идентификации клиента и до регистрации
входящего события. Telegram и VK показывают ссылки на оба документа и отдельные
кнопки «Согласен»/«Не согласен». Backend API для MAX готов, но отдельный работающий
MAX-адаптер в текущем репозитории отсутствует.

Отказ или отзыв блокирует новые операции, которым необходимо согласие. Данные
заказов не удаляются автоматически. После проверки оснований менеджер может
выполнить действие «Удалить карточки и обезличить связанные заказы»: карточка и
канальные идентификаторы удаляются, заказ остаётся, а имя, контакты, внешний ID,
адрес доставки и комментарий очищаются; в заказе фиксируется «Клиент удалён».
В карточке клиента хранится UUID актуального события реестра, а не URL файла.
Админка показывает дату, ссылку на запись и формируемую на лету выписку реестра.

## Сущности

```text
PersonalDataDocumentVersion
  ├─ document_type + version + effective_from
  ├─ immutable content + SHA-256 + permanent public_path
  └─ created_at

PersonalDataConsentEvent (append-only)
  ├─ public UUID, customer (optional)
  ├─ channel + identity type/value + identification level
  ├─ purpose + status + UTC occurred_at + expression method
  ├─ consent document + policy document
  ├─ minimal evidence JSON
  └─ previous_event → earlier event
```

Публичного API редактирования и удаления нет. В Django Admin события доступны
только пользователям со штатными model permissions и только для чтения.

## Создание новой версии

1. Создать две новые записи документов через Django Admin или Django shell, не
   изменяя старые записи.
2. Указать уникальные `version`, `effective_from` и `public_path`.
3. Проверить публичные страницы и хеши.
4. После наступления `effective_from` backend начнёт запрашивать новое согласие.

## Эксплуатация

- PostgreSQL, VPS, файловые и внешние резервные копии должны находиться на
  территории РФ, если это необходимо для соблюдения локализации данных граждан РФ.
- Реестр входит в обычное резервное копирование PostgreSQL. Проверка восстановления
  резервной копии должна выполняться по утверждённому оператором графику.
- Не включать `identity_value`, контакты, тексты переписки, токены и платёжные
  реквизиты в клиентские ошибки, метрики и внешние аналитические системы.
- Доступ сотрудников к Django Admin и резервным копиям должен журналироваться и
  регулярно пересматриваться.

## Организационный checklist перед коммерческой эксплуатацией

Пункты ниже не входят в обязательные шаги разработки и приёмки текущего учебного
MVP. В тестовом и демонстрационном контуре документы публикуются с явно видимыми
`TODO`. Перед коммерческой эксплуатацией и обработкой данных реальных клиентов
placeholders необходимо заменить фактическими сведениями и передать документы на
финальную проверку профильному юристу.

- полное наименование/ФИО оператора, ИНН/ОГРН(ИП), адрес;
- email и почтовый адрес для запросов и отзыва;
- точные юридические наименования, реквизиты и роли всех обработчиков;
- сроки хранения по каждой категории данных и порядок уничтожения;
- подтверждение российского размещения PostgreSQL, VPS и всех резервных копий;
- проверка трансграничной передачи для Telegram и иных внешних каналов;
- локальные акты, модель угроз, ответственные лица и порядок реагирования;
- финальная правовая проверка текста и фактических процессов профильным юристом.
