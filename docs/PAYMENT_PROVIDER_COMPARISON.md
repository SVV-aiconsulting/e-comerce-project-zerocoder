# Выбор платёжного провайдера для MVP

Дата анализа: 25.08.2026  
Статус: требуется подтверждение владельца проекта  
Рекомендация: **ЮKassa**

## 1. Требования WebMarket

Провайдер для MVP должен поддерживать:

- тестовый контур без списания денег;
- создание одноразовой ссылки на оплату подтверждённого заказа;
- идемпотентное создание платежа;
- серверное подтверждение результата, не зависящее от возврата клиента в браузер;
- полные и частичные возвраты;
- передачу товарных позиций для чеков по 54-ФЗ;
- работу из Telegram, VK, email и веб-формы через один backend;
- отдельные тестовые и production-реквизиты.

## 2. Сравнение

| Критерий | ЮKassa | Robokassa |
|---|---|---|
| Тестирование | Отдельный тестовый магазин; основные API, уведомления, возвраты и проверка чеков доступны без реальных списаний | Тестовый режим `IsTest=1`; отдельные тестовые пароли №1 и №2 |
| Ссылка на оплату | `POST /v3/payments` с redirect-confirmation возвращает `confirmation_url` | Invoice API возвращает одноразовую или многоразовую ссылку |
| Идемпотентность | Нативный `Idempotence-Key` для изменяющих запросов, гарантия в течение 24 часов | Нативного аналога для создания счёта в изученном Invoice API нет; защиту от дублей нужно обеспечивать в WebMarket по `InvId` и состоянию локальной операции |
| Уведомления | JSON webhook; после получения WebMarket повторно запрашивает объект платежа по API и только затем меняет CRM-статус | `ResultURL` с проверкой контрольной суммы и ответом `OK{InvId}`; дополнительно доступен `ResultUrl2` в JWS |
| Возвраты | Единый REST API `/v3/refunds`, полный и частичный возврат, ключ идемпотентности | Отдельный Refund API, JWT с дополнительным `Password3`, отдельная проверка статуса возврата |
| Чеки | Передача `receipt` при платеже/возврате, тестовый режим проверки чеков, поддержка разных сценариев формирования | Передача `Receipt`/`InvoiceItems`, участие номенклатуры в подписи, фискализация через подключённую схему Robokassa |
| Сложность секретов | `shop_id` и `secret_key` для обычного магазина | `MerchantLogin`, рабочие и тестовые пароли №1/№2, а для возвратов ещё `Password3` |
| Соответствие архитектуре | Один JSON REST API хорошо ложится на тонкий `httpx`-клиент, аудит и конечный автомат | Функционально подходит, но требует нескольких схем подписи и интерфейсов |

## 3. Вывод

Для WebMarket рекомендуется **ЮKassa**. Главный аргумент — не бренд и не количество
способов оплаты, а реализуемость надёжного MVP: единая модель API, нативная
идемпотентность, простой redirect-flow и единообразные объекты платежа/возврата уменьшают
объём специальной криптографической и интеграционной логики.

Robokassa остаётся корректной альтернативой, если у владельца проекта уже есть
подключённый магазин, выгодные коммерческие условия или требование использовать именно
её. Комиссии намеренно не используются как решающий технический критерий: они зависят от
договора, типа бизнеса и подключённых способов оплаты и должны сравниваться по офертам,
доступным владельцу магазина.

## 4. Предлагаемая реализация с ЮKassa

После подтверждения выбора:

1. добавить `Payment`, `PaymentWebhookEvent` и `Refund` с уникальными внешними ID;
2. сделать тонкий клиент ЮKassa без доступа к ORM;
3. создавать один redirect-платёж для подтверждённого заказа с детерминированным ключом
   идемпотентности и `metadata.order_id`;
4. отправлять клиенту `confirmation_url` через текущий канал;
5. принимать `payment.succeeded` и `payment.canceled`, сохранять сырой безопасный аудит;
6. перед изменением CRM-статуса обязательно получать платеж по API и сверять внешний ID,
   сумму, валюту, заказ и финальный статус;
7. только после подтверждённой предоплаты разрешать `offers/confirm` Яндекс Доставки;
8. передавать номенклатуру заказа и доставки в `receipt`;
9. покрыть создание, повтор webhook, поддельное событие, неверную сумму, отмену и возврат
   contract-тестами через `httpx.MockTransport`;
10. держать production-магазин выключенным отдельным явным флагом до релизного чек-листа.

## 5. Важная граница чеков

Платёжная ссылка, запись данных чека и сам фискальный чек — разные сущности. WebMarket
сформирует состав расчёта и передаст его ЮKassa, однако настоящий фискальный чек в
production появится только после выбора и подключения совместимого сценария онлайн-кассы
в личном кабинете. В тестовом магазине проверяется формат и жизненный цикл, но тестовые
данные не уходят в ОФД.
