# Техническое задание: AI-система обработки заказов WebMarket

Версия: 0.1 (черновик)  
Дата: 24.08.2026  
Статус: документ развивается вместе с реализацией

## 1. Назначение

Система предназначена для автоматизации продаж e-commerce через несколько каналов.
Она принимает обращения на естественном языке, формирует структурированный черновик,
уточняет недостающие сведения, рассчитывает заказ и после подтверждения клиента
автоматически создаёт его в PostgreSQL CRM, оформляет доставку и предоставляет ссылку
на оплату.

## 2. Цели

- Минимизировать участие менеджера в типовом процессе продажи.
- Обеспечить единый процесс для Telegram, VK, email и web.
- Использовать LLM там, где требуется понимание языка и контекста.
- Сохранить точные и финансовые операции детерминированными и проверяемыми.
- Обеспечить аудит каждого этапа от входящего сообщения до оплаты.

## 3. Роли

- **Клиент** создаёт и уточняет заказ, подтверждает итог, оплачивает его.
- **Менеджер** работает с исключениями и контролирует заказы в dashboard.
- **Администратор** управляет каталогом, интеграциями и настройками.
- **AI-ассистент** понимает запрос и ведёт диалог, не выполняя произвольные записи в БД.

## 4. Основной пользовательский сценарий

1. Клиент отправляет свободный запрос через поддерживаемый канал.
2. Адаптер создаёт единое входящее событие.
3. Фоновый обработчик передаёт текст LLM.
4. LLM возвращает структурированный `OrderIntent`.
5. Backend сопоставляет позиции с фактическим каталогом и валидирует данные.
6. При нехватке данных система задаёт клиенту один конкретный вопрос.
7. После заполнения обязательных полей создаётся `OrderDraft` и preview стоимости.
8. Клиент явно подтверждает состав и сумму.
9. Backend транзакционно создаёт заказ в CRM.
10. Система создаёт/подтверждает доставку согласно выбранной интеграции.
11. Платёжный сервис формирует ссылку на оплату.
12. Проверенный webhook переводит платёж и заказ в соответствующий статус.
13. Клиент и менеджер получают уведомления.

## 5. Функциональные требования

### 5.1 Каналы

- Обязательные: Telegram, email, web.
- Дополнительные: VK, MAX.
- Все каналы используют единый backend и не дублируют бизнес-логику.
- Повторное внешнее событие не создаёт дубликат заявки.

### 5.1.1 Идентификация клиента между каналами

- Для Telegram, VK и MAX основной ключ — `(channel, external_user_id)`.
- Для email основной ключ канала строится из нормализованного адреса отправителя.
- Новый ID одного канала не присоединяется к карточке другого канала только из-за
  совпадения телефона или email.
- Совпадение контактов создаёт `CustomerIdentityConflict`; оно не блокирует сбор,
  создание, доставку или оплату заказа.
- Временные карточки с одинаковым телефоном/email допустимы до решения менеджера.
- SMS-аутентификация не входит в текущий MVP.
- Веб-форма не использует UUID сессии как идентификатор клиента. Она ищет карточку
  непосредственно по нормализованному телефону/email.
- Если веб-контакты однозначно указывают на одну карточку, заказ связывается с ней.
  При нескольких кандидатах создаётся новая карточка и неблокирующие конфликты.
- Технический UUID веб-формы используется только для идемпотентности отправки,
  корреляции диалога и доступа к статусу конкретного обращения.
- GigaChat не выбирает карточку и не разрешает конфликты идентификации.

### 5.2 AI/NLU

- Определение намерения: новый заказ, изменение, отмена, вопрос, другое.
- Извлечение товара, количества, единицы, адреса, даты, времени, доставки,
  оплаты и комментария.
- Strict structured output по версионируемой схеме.
- Поддержка контекста диалога и исправлений клиента.
- Обнаружение отсутствующих и неоднозначных полей.
- Запрет на использование выдуманной цены, наличия или свойства товара.

### 5.3 Черновик и подтверждение

- Черновик хранится в PostgreSQL и связан с клиентом, каналом и сообщениями.
- Каждая позиция ссылается на фактический товар либо имеет статус `unresolved`.
- Заказ нельзя создать без обязательных данных и явного подтверждения клиента.
- Изменение после preview требует повторного расчёта и подтверждения.

### 5.4 CRM и заказ

- PostgreSQL является источником истины.
- Заказ создаётся существующим сервисным слоем WebMarket.
- Сохраняются снимки товара, цены и клиента.
- Сохраняются снимки телефона, email и ID пользователя/обращения текущего канала.
- Ведётся история бизнес-статусов и источников изменений.
- Заказ продолжает выполняться при открытом конфликте идентификации; отсутствие
  обязательного для доставки контакта обрабатывается отдельно как недостающее поле.

### 5.5 Доставка

- Для MVP используется API «Яндекс Доставка по России» в test-контуре.
- Расчёт стоимости и срока выполняет backend, LLM не вызывает API доставки.
- Для внешнего расчёта каталог хранит вес и габариты единицы товара.
- Для курьерской доставки обязательны адрес и телефон получателя.
- Наличные при получении не передаются в Яндекс: используются предоплата либо карта
  при получении.
- Сохраняются предварительный quote, оффер и внешняя заявка.
- Синхронизация статусов и трек-данных.
- Обработка ошибки, отмены и ручного fallback.
- Production требует отдельные коммерческие токен/склад и явный предохранитель.

### 5.6 Оплата

- Провайдер MVP: ЮKassa; разработка и первое развёртывание используют test shop.
- Создание redirect-ссылки только для подтверждённого заказа и только при
  `card_prepayment`.
- Идемпотентность создания платежа через `Idempotence-Key` и уникальную запись `Payment`.
- Проверка webhook по официальной сети IP и обязательное получение актуального платежа
  через API с проверкой суммы, валюты и номера заказа в metadata.
- Состояния ожидания, успешной оплаты, отмены, ошибки, истечения и возврата хранятся в
  `Payment`/`Refund`; каждое входящее событие — в `PaymentWebhookEvent`.
- В `receipt` сохраняются позиции, доставка, контакт покупателя и данные для 54-ФЗ.
- Production требует отдельных реквизитов, HTTPS и
  `YOOKASSA_PRODUCTION_ENABLED=True`.

### 5.7 Dashboard

- Поиск и фильтры по заказам и заявкам.
- Просмотр входного текста, результата AI и истории уточнений.
- Очередь исключений для менеджера.
- Метрики заказов, каналов, оплат, доставок и автоматизации.

## 6. Нефункциональные требования

- Идемпотентность внешних событий, создания заказов и платежей.
- Транзакционность критических изменений.
- Асинхронная обработка через общую очередь.
- Повторные попытки с ограничением и журналом ошибок.
- Не хранить API-ключи и персональные данные в промпт-библиотеке и логах.
- HTTPS для production webhook и платёжных сценариев.
- Наблюдаемость: correlation ID, длительность, статус и причина ошибки.
- Возможность отключить LLM и передать заявку менеджеру без потери данных.

## 7. Ограничения LLM

- Нет прямого SQL/ORM-доступа.
- Нет самостоятельного изменения CRM.
- Нет права создавать заказ без подтверждения клиента.
- Нет права создавать или подтверждать оплату.
- Нет права рассчитывать цены и доставку собственными рассуждениями.
- Все результаты считаются недоверенными входными данными до валидации.

## 8. Предварительные сущности

- `InboundEvent`
- `OrderDraft`
- `OrderDraftItem`
- `AIExtractionRun`
- `Clarification`
- `CustomerIdentityConflict`
- `DeliveryQuote`
- `Shipment`
- `DeliverySyncEvent`
- `Payment`
- `PaymentWebhookEvent`
- `Invoice`/`Receipt` при необходимости отдельного хранения

Поля и связи будут зафиксированы до создания миграций этапа 1.

## 9. Предварительные API endpoints

- `POST /api/inbound-events/` — доверенный приём события адаптером.
- `GET /api/order-drafts/{id}/` — состояние черновика.
- `POST /api/order-drafts/{id}/messages/` — ответ на уточнение.
- `POST /api/order-drafts/{id}/confirm/` — подтверждение клиента.
- `POST /api/delivery/quotes/` — расчёт доставки.
- `POST /api/orders/{number}/payments/` — создание оплаты.
- `POST /api/webhooks/payments/{provider}/` — платёжный webhook.
- `POST /api/webhooks/delivery/{provider}/` — webhook доставки при наличии.

Точные URL, права доступа и схемы будут уточнены перед реализацией.

## 10. Критерии приёмки AI-MVP

Система должна обработать запрос наподобие:

> Привезите завтра после шести две упаковки тигровых креветок на Ленина 15,
> оплачу картой.

Без участия менеджера система должна:

1. определить создание заказа;
2. извлечь товар, количество, адрес, дату, время и оплату;
3. найти фактический товар либо запросить уточнение;
4. рассчитать сумму и доставку серверными сервисами;
5. показать состав и итог клиенту;
6. дождаться явного подтверждения;
7. создать ровно один заказ в CRM;
8. предоставить ссылку на оплату;
9. принять webhook и обновить статус;
10. сохранить аудит всех этапов.
